# Historical-store upgrade checks (#290)

The integration tier opens real historical stores using the current SwiftData schema and automatic
lightweight migration. It also runs the application lifecycle that interprets the old review baseline:
activation, media-filter changes, reconciliation, and reopening through a fresh container.

`MigrationFixtureTests` asserts stored `includePhotos` directly. `.media == .photosOnly` alone cannot
prove backfill: the defensive `(false, false)` decode also yields `.photosOnly`. `ReviewBaselineTests`
covers pure interpretation; it cannot replace the lifecycle and disk-durability tests.

## 1.0.2 provenance and fixture contents

The source is `411846193f779590f8b30e5979703afafc25c055`, verified from the release workflows:

- [TestFlight run 21](https://github.com/valtteriluomapareto/poimi/actions/runs/32235061172)
  archived **1.0.2 (21)** and confirmed ASC processing state **VALID**.
- [App Store attachment run 14](https://github.com/valtteriluomapareto/poimi/actions/runs/32240550827)
  attached **1.0.2 (21)** to the **1.0.2** draft. Submission/release remain manual steps.

This is a synthetic store generated by rebuilding that source, not a user's database or a store
extracted from the signed release binary. Its generator toolchain, SDK, simulator runtime/build,
source revision, seed-harness hash and file checksums are recorded in
`App/PoimiAppTests/Fixtures/1.0.2/manifest.json`. Historical-runtime coverage is limited to that recorded
runtime; the release device check below remains necessary.

The fixture contains two exported albums: photos only and photos with videos enabled. Their settings,
identities, date ranges, picks, done days, export snapshots/counts/timestamps, destination identifiers,
and resume state are known. A geocoded-name cache entry has a fixed cell, name and timestamp.

Each album has a flat review-baseline blob with:

- `2025-07-05`: `photo-1`, plus `video-1` when enabled, plus 20,000 deterministic padding identifiers;
- `2025-07-06`: `photo-next`;
- `undated`: `undated-photo`.

Padding identifiers are `fixture-photo-%05d-` for indices 0..<20,000 followed by 64 `x` characters.
They make the blob large enough to exercise external storage on the recorded runtime. Generation
requires an actual external file whose SHA-256 matches each baseline. Integration tests check bundled
file hashes, exact legacy bytes, and the independently reconstructed baseline contents. The large
identifiers are synthetic strings; no Photos access or image bytes are needed.

## Generate a fixture

Use an installed iOS 26 simulator runtime. Resolve the actual release build's source SHA from ASC's
build number and TestFlight history as described in [the release runbook](testflight-setup.md), rather
than assuming the version-bump commit was shipped. The revision must exist in local git history.

For the initial fixture:

```sh
Scripts/generate-migration-fixture.py \
  --revision 411846193f779590f8b30e5979703afafc25c055 \
  --runtime com.apple.CoreSimulator.SimRuntime.iOS-26-2 \
  --testflight-run https://github.com/valtteriluomapareto/poimi/actions/runs/32235061172 \
  --output /tmp/poimi-fixture-1.0.2
```

The output directory must not exist. The script exports the revision to a temporary source directory,
appends `Scripts/migration/FixtureSeed.swift` to its existing **test-only** `TestSupport.swift`, and runs
only `MigrationFixtureSeed`. It does not patch any production model, schema, or application source.
The app and its tests are built together with their historical module/entity identity. It creates,
boots, and finally deletes its own simulator, leaving existing simulator installs alone. Build/test
output is retained at `build/migration-fixture-generation.log`.

The seeder saves into a separate disk-backed container under the disposable app's Documents directory.
After the test exits, the script shuts down the simulator, copies the entire fixture directory,
checkpoints the WAL, checks SQLite integrity, and verifies external-storage files before publishing
the output. Neither `DebugScreen` (which seeds in-memory stores) nor `-PoimiUseFakeLibrary` alone can
produce this fixture.

Review the output and its manifest, then copy the **whole directory**, including hidden directories,
into `App/PoimiAppTests/Fixtures/<version>/`. The `.xcodeproj` includes `Fixtures` as a folder resource
of the test target only. Never open the committed store in place: every test makes a fresh temporary
copy. Do not copy only `default.store` or omit its adjacent external files.

Generation is reproducible at the level of schema and expected records. SQLite UUIDs, external file
names, metadata and set serialization can change between runs, so byte-for-byte identical regeneration
is not promised. Each committed fixture's own bytes and checksums are immutable.

For future formats, adapt or version the test-only seed harness to the historical APIs and record the
change in the manifest. The current harness targets 1.0.2's initializer and flat-blob format; it is not
an automatic arbitrary-version seed converter. Production model definitions must remain untouched.

## Run the tests and prove they can fail

Use any available iOS 26 simulator for the current application:

```sh
xcodebuild test -project App/PoimiApp.xcodeproj -scheme PoimiApp \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  -only-testing:PoimiAppTests/MigrationFixtureTests \
  -only-testing:PoimiAppTests/ReviewBaselineTests \
  CODE_SIGNING_ALLOWED=NO
```

These suites are included automatically in the normal CI integration tier. No historical app build
is needed on a PR: CI reads the committed fixture.

Before merging changes to these tests, perform both mutations in a disposable checkout or with an
exact backup of the changed source. Restore the source after each mutation, even if a command fails.

1. Change **only the stored declaration** `var includePhotos: Bool = true` to `false`. Leave constructor
   and factory defaults alone. `MigrationFixtureTests.preservation` must fail at the direct bool check
   (and at media selection for the album with videos). Run tests directly, without the grep guard.
2. Restore the pre-#289 adoption behavior: remove activation-time conversion and adopt a nonempty flat
   blob under the current lens inside `reconcile`, retaining its `previous != current` save gate.
   The historical filter-switch tests must fail. Simply deleting all adoption is a different mutation;
   the new-candidate test guards against that failure mode as well.

Also keep activation durability isolated: its test must not call `deactivate`, `flushNow`, or
`context.save` after activation. Autosave is disabled and the container scope is released before a
fresh open, so later persistence cannot mask a missing migration save.

Record failing assertions, restored passing results, and observed runtime in the implementation PR.
A mutation surviving does not uniquely diagnose a missing sidecar: inspect fixture contents, lifecycle
sequences, and assertions too.

## Fixture maintenance and remaining defaults guards

Add fixtures for distinct **persisted schemas or blob formats**, not every marketing release. Keep
representative older fixtures so users skipping intermediate releases retain direct-upgrade coverage.
Do not replace an old fixture by opening and re-saving it using current models.

The 1.0.2 fixture replaces the `includePhotos` grep check. It cannot exercise the original backfill of
`includeVideos` or `locationEnabled`, because both attributes already exist in its schema. Their checks
remain in `Scripts/check-migration-defaults.sh` until fixtures predating those fields (or equivalent
behavioral coverage) prove the defaults. Pure decoder tests do not cover schema backfill.

Production continues to use automatic lightweight migration. No staged migration plan or frozen
production models are introduced for testing.

## Release checklist: install over the previous build

Full old-build/install/upgrade automation is a separate follow-up. For now:

1. Identify the previous release's build and commit, and record the candidate build identity.
2. On a dedicated test device, install the previous release. Create known albums with photos-only and
   photos-and-videos settings, picks, done days, an export, and resume state. Record the expected state.
   Keep the Photos library unchanged during the filter-switch checks.
3. Install the candidate **over** that app without uninstalling or clearing its data. Prefer the exact
   signed/TestFlight build intended for release. Launch and confirm both albums and their settings,
   picks, done marks, export status, destination, and resume state survived.
4. Open an upgraded album's Overview, change media in Settings **before entering review**, then enter
   the review grid. Done days must survive. Switch back and enter review again to verify preservation.
   With a separately seeded prior-build install, first enter the review grid with unchanged media,
   return to Settings, change media, and enter review again. The Overview scans automatically but does
   not reconcile done days; entering review is what distinguishes these two sequences.
   Force-quit/relaunch to confirm durability.
5. Add a genuinely new photo within a previously reviewed lens and confirm only the affected done day
   reopens. Verify export status using the app, not just database fields: status is derived behavior.
6. Record device/OS, old/new builds, scenarios, and results with the release check. The fixture suite
   separately verifies synthetic geocode cache records without relying on live geocoder responses.

A future automated runner can reuse the historical seeder on a disposable simulator and then install
the candidate app over the seeded data. It will need to place the fixture at the app's actual store
location (the generator deliberately writes a separate store), drive application-level activation and
reconciliation, and assert derived behavior. SQLite inspection can supplement those checks but cannot
replace them. Rebuilding historical apps belongs at release time, not in every PR's CI.

## Initial validation (2026-09-14)

Fixture generation passed on iOS 26.2 (23C54), using Xcode 26.6 (17F113), SDK 26.5. The current app
opened it on iOS 26.5. The two external blobs and SQLite store total 3,553,902 bytes; all manifest
checksums were verified after testing.

- New suites: 10 test declarations (25 individual cases), approximately 4.9 seconds in a focused run.
- Full app integration suite: 341 tests in 46 suites passed (9.1 seconds of test execution).
- Pure domain: 211 tests in 28 suites passed. Release simulator build, all nine guards and their
  self-tests passed. Changed Swift files introduce no lint warnings; existing repository warnings remain.
- Flipping only the stored `includePhotos` default failed the direct stored-bool assertions.
- Restoring the actual pre-#289 `DoneStore` source failed both photos-to-both filter-switch sequences:
  July 5 lost its done mark, including after reopening the store.
- Removing only the activation save failed the fresh-container assertions for both historical lenses.

All mutations were restored before the passing full-suite and Release checks. These timings describe
test execution, not simulator startup/build time. The actual signed-build device checklist was not
performed as part of this implementation; it remains a release check.
